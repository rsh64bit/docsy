Pattern Matching

Variable declaration without let — patterns are declarations
18 slides · from match arms to advanced bindings
Motivation

Where is epb declared?

The code has no let, yet a variable appears
match block.unwrap() {
    Block::EnhancedPacket(epb) => {
        // epb is usable here — but where was it declared?
    }
}
Answer: epb is declared right there in the pattern. The pattern is the declaration.
Concept

Three operations in one line

A match arm does check + destructure + bind simultaneously
Block::EnhancedPacket(epb) => { ... }
StepWhat happens
1. CheckIs the variant Block::EnhancedPacket?
2. DestructureExtract the data inside the variant
3. BindName that data epb
Rust philosophy: pattern matching is declaration. Anywhere you write a pattern, you can introduce new variables — no let required.
Syntax

match expressions

The most common place patterns appear
match some_enum {
    Variant::A(x) => {},              // x declared here
    Variant::B { field: y } => {},   // y declared here
}

Each arm introduces its own variables. They are scoped to that arm's body — x doesn't exist in the B arm.

With guards

match value {
    n if n > 0 => println!("positive: {n}"),
    n => println!("non-positive: {n}"),
}
Syntax

if let expressions

When you only care about one variant
if let Some(value) = optional {
    // 'value' exists only in this block
    println!("{}", value);
}

Equivalent to a match with one arm + a wildcard, but more concise.

Chained

if let Some(pkt) = packets.next() {
    if let Ok(eth) = EthernetPacket::new(&pkt) {
        process(&eth);
    }
}
Syntax

for loops

The loop variable is a pattern
// simple binding
for item in vec {}

// tuple destructure
for (index, value) in vec.iter().enumerate() {}

// map destructure
for (key, value) in &hashmap {}
Every for x in iter is a pattern. You've been using pattern matching since day one — for item in vec binds item via a pattern.
Syntax

Function parameters

Parameters are patterns too
// destructure a tuple in the signature
fn process((x, y): (i32, i32)) {
    println!("x={x}, y={y}");
}

// destructure a struct in the signature
fn handle(Point { x, y }: Point) {
    println!("({x}, {y})");
}

// closures too
let sum = |(a, b): (i32, i32)| a + b;
Syntax

let destructuring

let itself is a pattern — it's patterns all the way down
// tuple
let (x, y) = (10, 20);

// struct
let Point { x, y } = point;

// array
let [first, second, ..] = arr;

// nested
let (Some(name), age) = (get_name(), 25) else {
    return;
};
Even let x = 5; is a pattern — x is an irrefutable pattern that binds to any value. Every let is pattern matching.
Syntax

while let & let else

Two more pattern sites you'll use often

while let

while let Some(item) = iter.next() {
    process(item);
}
// loop ends when pattern
// stops matching (None)

Common for iterators and channel receivers.

let else (Rust 1.65+)

let Some(value) = optional else {
    return Err("missing");
};
// value is in scope here
// the else must diverge

Like an inverted if let — the happy path is flat.

Advanced

@ bindings

Bind a variable AND test it against a pattern at once
match age {
    teen @ 13..=19 => {
        println!("teenager aged {teen}");
    }
    child @ 0..=12 => {
        println!("child aged {child}");
    }
    adult => {
        println!("adult aged {adult}");
    }
}

Without @, you can match a range but not name the value. With @, you get both.

Nested @ binding

match msg {
    Message::Move { x: x_val @ 0..=100, .. } => {
        println!("valid x: {x_val}");
    }
    _ => {}
}
Advanced

ref and ref mut

Borrow inside a pattern instead of moving
let name = String::from("atlas");

match name {
    ref n => {
        // n is &String, name is NOT moved
        println!("borrowed: {n}");
    }
}

// name is still usable here
println!("{name}");

Without ref

match name {
    n => {}  // n takes ownership
}
// name is MOVED, can't use

With ref

match name {
    ref n => {}  // n borrows
}
// name is still alive
ref mut gives a mutable borrow. In modern Rust, match &value often replaces explicit ref, but you'll see ref in older code and when matching owned values.

Where patterns appear

Design

Why Rust designed it this way

Patterns-as-declarations serve four goals
GoalHow patterns achieve it
ConcisenessMatch + destructure + bind in one expression
SafetyVariables only exist in the matched scope
ExhaustivenessCompiler verifies you handle all variants
Type inferenceTypes are known from the pattern — no annotations needed

Compare with C

// C: manual, no safety
if (pkt->type == PKT_ICMP) {
    icmp_t *icmp = pkt->data;
    // hope data is really icmp...
}
// Rust: compiler-checked
match pkt {
    Packet::Icmp(icmp) => {
        // icmp is guaranteed correct
    }
    _ => {}
}

Spot the variables

How many variables does this pattern declare?
match result {
    Ok((code, Message::Text(msg))) => {
        println!("code={code}, msg={msg}");
    },
    Err(e) => {
        eprintln!("error: {e}");
    }
}

Answer

VariableBound fromScope
codeFirst element of the Ok tupleOk arm only
msgInner data of Message::TextOk arm only
eError value inside ErrErr arm only
Three variables, each scoped to its own arm. Nested patterns extract from nested structures in a single expression.
Practice

Matching a function that returns Option<T>

Six ways to handle the Some / None pattern
fn find_user(id: u32) -> Option<String> {
    if id == 1 { Some("atlas".to_string()) } else { None }
}

match

match find_user(1) {
    Some(name) => println!("found {name}"),
    None => println!("no user"),
}

if let

if let Some(name) = find_user(1) {
    println!("found {name}");
} else {
    println!("no user");
}

let else

let Some(name) = find_user(1) else {
    println!("no user");
    return;
};
// name is in scope, happy path stays flat
println!("found {name}");

? operator

fn greet(id: u32) -> Option<String> {
    let name = find_user(id)?;
    // early-returns None if find_user did
    Some(format!("hi {name}"))
}
Practice

Chaining without unwrapping: combinators

map, and_then, unwrap_or — no explicit match needed
let greeting: Option<String> = find_user(1)
    .map(|name| format!("hello, {name}"));   // Some -> Some, None -> None

let len: Option<usize> = find_user(1)
    .and_then(|name| if name.is_empty() { None } else { Some(name.len()) });

let display: String = find_user(99)
    .unwrap_or_else(|| "guest".to_string());   // fallback on None
CombinatorSome(x) doesNone does
map(f)returns Some(f(x))returns None
and_then(f)returns f(x) (f itself returns an Option)returns None
unwrap_or(d)returns xreturns d
unwrap_or_else(f)returns xreturns f()
These are just match under the hood — use them when you're transforming the value, and switch back to explicit match/if let when the branches do meaningfully different things (like printing vs. returning).
Deep dive

Option::map in detail

Transform the value inside Some, leave None untouched
let greeting: Option<String> = find_user(1)
    .map(|name| format!("hello, {name}"));   // Some -> Some, None -> None

map takes a closure FnOnce(T) -> U and applies it only if the Option<T> is Some. The closure never runs on None — there's nothing to hand it. The result is always an Option<U>, so "optionality" is preserved through the transformation.

What it desugars to

fn map<T, U>(self, f: impl FnOnce(T) -> U) -> Option<U> {
    match self {
        Some(x) => Some(f(x)),   // run f, rewrap in Some
        None => None,          // skip f entirely, stay None
    }
}

Tracing both paths

CallInside mapResult
find_user(1) → Some("atlas")closure runs: format!("hello, atlas")Some("hello, atlas")
find_user(99) → Noneclosure never calledNone

Manual equivalent

let greeting = match find_user(1) {
    Some(name) => Some(format!("hello, {name}")),
    None => None,
};

Same behavior, more ceremony.

Chaining maps

let shout = find_user(1)
    .map(|n| n.to_uppercase())
    .map(|n| format!("{n}!"));
// Option<String> -> Option<String> -> Option<String>

Each map only fires if the previous one produced Some.

Reach for map when: you're changing the type/shape of the inner value but the Some/None-ness itself doesn't change. Reach for and_then instead when: your closure itself might fail or produce nothing (i.e. it returns another Option) — using map there would give you Option<Option<U>>, a common beginner trip-up.

Matching Option<(A, B, C)>

The pcap analyzer's IcmpReport.resp field
struct IcmpReport {
    ident: u16,
    seq: u16,
    req_src_ip: Ipv4Addr,
    req_dst_ip: Ipv4Addr,
    resp: Option<(Ipv4Addr, Ipv4Addr, Duration)>,  // None = no reply seen (NOK)
}

A 3-tuple wrapped in Option is still just one pattern — destructure the tuple right inside the Some(...):

match &entry.resp {
    Some((resp_src, resp_dst, rtt)) => {
        println!("OK  {} -> {}  rtt={:?}", resp_src, resp_dst, rtt);
    }
    None => {
        println!("NOK seq={} ident={}", entry.seq, entry.ident);
    }
}
Note: Option<A, B, C> is not valid Rust — Option<T> takes exactly one type parameter. To hold three values, wrap a tuple: Option<(A, B, C)>. The extra parentheses are what make it one type argument.
