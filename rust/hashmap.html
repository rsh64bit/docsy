HashMap

Matching ICMP requests to replies without relying on stack order
7 slides · from Eq/Hash to a real tracking use case
Motivation

Why not a stack?

Ping requests and replies don't arrive LIFO
// two requests fired before any reply comes back
Request  ident=1, seq=0    -> push
Request  ident=1, seq=1    -> push

// reply for the OLDER request arrives first
Reply    ident=1, seq=0    -> pop() gives seq=1’s request — wrong pair
Pop gives you the most recent push, not the correct match. The right pairing key is (ident, seq), not arrival order on a stack.
Concept

HashMap<K, V>

Part of std::collections — no external crate needed
use std::collections::HashMap;

let mut pending: HashMap<u16, PendingPing> = HashMap::new();
pending.insert(ident, entry);
pending.remove(&ident);

A key-value store: given a key, look up, insert, or remove its value in roughly constant time — no linear scan required.

Requirement: K must implement Eq + Hash. Built-in types like u16, String, tuples of hashable types — already satisfy this.
Concept

Why Eq, not just PartialEq

A hashmap needs a key that is always equal to itself
trait PartialEq { fn eq(&self, other: &Self) -> bool; }
trait Eq: PartialEq {}  // promise: eq is reflexive, no exceptions

// f64::NAN breaks reflexivity — NAN == NAN is false
// so f64 implements PartialEq but NOT Eq

Lookup works by: compute hash(key) to find the bucket, then compare with == to confirm the match. If a key weren’t guaranteed equal to itself, you could insert a value and never retrieve it back.

Eq is the compiler-enforced guarantee that lookups are reliable. That's why HashMap<K, V> requires K: Eq, not merely PartialEq.
Syntax

Deriving a custom key

derive checks that every field is itself Eq + Hash
#[derive(Hash, Eq, PartialEq, Debug)]
struct PingKey {
    ident: u16,
    src_ip: Ipv4Addr,
}
DeriveGives you
PartialEqthe == / != operators
Eqthe reflexivity promise HashMap requires
Hasha .hash() impl so HashMap can bucket it
Debug{:?} formatting for logging
Both u16 and Ipv4Addr are already Eq, so this derive succeeds trivially — no NaN-like landmines in either field.
Syntax

The Entry API

Get-or-insert without writing the if/else yourself
// insert only if the key doesn't already exist
player_stats.entry("health").or_insert(100);

// modify in place, or insert a default if absent
player_stats.entry("mana")
    .and_modify(|m| *m += 200)
    .or_insert(100);

Applied to the ping tracker — get the queue for an ident if it exists, or create an empty one first:

pending.entry(ident).or_default().push_back(entry);
Applied

HashMap of queues, not a stack

When seq is always 0, arrival order is the only signal left
use std::collections::{HashMap, VecDeque};

let mut pending: HashMap<u16, VecDeque<PendingPing>> = HashMap::new();

// on request
pending.entry(ident).or_default().push_back(PendingPing { .. });

// on reply — pop the OLDEST outstanding request for this ident
match pending.get_mut(&ident).and_then(|q| q.pop_front()) {
    Some(req) => { /* matched pair */ }
    None    => { /* orphan reply */ }
}

// at end: anything left in any queue = unanswered requests
Stack vs queue: pop from the front, not the top — replies come back in the order requests were sent. Only trust this within one ident, and only if the network doesn't reorder packets.
