Ownership & Move Semantics

Why passing a value can quietly kill it — and how to spot it before the compiler does
10 slides · Copy vs move · scalars vs structs · fixing E0382
Motivation

Pass x to a function, then reassign it — error?

The instinct says yes. Rust says: depends on the type.
fn test(x: u32) { println!("{}", x); }

fn main() {
    let mut x: u32 = 10;
    test(x);   // passed by value
    x = 14;  // reassigned after
    test(x);   // used again
}
This compiles fine. No move error here at all — because u32 is a scalar type. The real question is: what happens with a type that isn't a scalar?
Concept

Two ways a value can be passed

The Copy trait decides which one happens
Type kindWhat happens on fn(x)Original x after?
Implements Copy (u32, bool, char, ...)Bits are duplicatedstill valid
Does not implement Copy (String, Vec, most structs)Ownership moves into the functioninvalidated
Ownership rules apply to every value. Scalars don't dodge the rule — they just never notice it, because Copy means the compiler duplicates instead of invalidating.

The part people miss

Reassignment is always legal, move or not — it doesn't need the old value to be alive, it just overwrites the binding. The error only appears if you read the old value after a move and before reassigning.

Error case · 1

Moving a String, then reading it

String is not Copy — it owns a heap allocation
fn test(x: String) { println!("{}", x); }

fn main() {
    let mut x: String = String::from("hello");
    test(x);                    // x moved into test
    println!("{}", x);   // x used after move
    x = String::from("world");
    test(x);
}
x = "hello" → test(x) moves it → x read here
Why: test(x) takes ownership. Once inside the function, main's x is gone. The very next line tries to read it — compiler refuses.
Error case · 1 (continued)

What cargo build actually prints

E0382 — borrow of moved value
error[E0382]: borrow of moved value: `x` --> src/main.rs:8:20 | 6 | let mut x: String = String::from("hello"); | ----- move occurs because `x` has type `String`, which does not implement the `Copy` trait 7 | test(x); | - value moved here 8 | println!("{}", x); | ^ value borrowed here after move | help: consider cloning the value if the performance cost is acceptable | 7 | test(x.clone()); | ++++++++
The compiler names the exact cause (String isn't Copy), the exact move point (line 7), and the exact bad read (line 8) — and even suggests a fix.
Concept · before the error

A struct made of scalars is still not scalar

Composite types don't inherit Copy from their fields
struct Strct { x: u32, y: u32, z: u32 }  // all fields Copy...
                                            // ...but Strct itself is NOT Copy

fn ownership_strcut(s: Strct) {
    let mut y: Strct = Strct { x: 0, y: 0, z: 0 };
    y = s;   // moves s into y — fine, nothing read after
}

fn main() {
    let s = Strct { x: 0, y: 1, z: 2 };
    ownership_strcut(s);   // s moved into the function
    // s never touched again — compiles clean
}
Copy must be derived explicitlystack-only ≠ Copy

Strct is entirely stack data, yet it still moves like a heap type would — because nobody wrote #[derive(Copy)]. This version compiles because neither move point is followed by a read of the old value.

Error case · 2

Same struct, now read after each move

One move inside the function, one move at the call site — two separate errors
fn ownership_strcut(s: Strct) {
    let mut y: Strct = Strct { x: 0, y: 0, z: 0 };
    y = s;                     // s moved into y
    println!("{}", s.y);   // s read after move — ERROR #1
}

fn main() {
    let s = Strct { x: 0, y: 1, z: 2 };
    ownership_strcut(s);          // s moved into the call
    println!("{}", s.y);   // s read after move — ERROR #2
}
Same rule (E0382), triggered at two independent move points: inside the function body, and at the call site in main. Ownership doesn't care which stack frame moved it.
Mental model

It's never "stack vs. heap"

It's always: does this type implement Copy?
TypeWhere storedCopy?Passing it
u32stackyescopies
struct { x: u32 } (no derive)stacknomoves
Box<u32>heapnomoves
Stringheapnomoves
Stack-only data is usually Copy, which is why the correlation feels causal — but a plain stack struct still moves unless you explicitly opt in with #[derive(Copy, Clone)]. The trait is the switch, not the memory location.
Fix

Four ways to stop the move error

Pick based on whether you need the original value again

1. Reassign instead of reading

test(x);
x = String::from("world"); // no read of old x
test(x);

Use when you don't need the old value at all.

2. Borrow instead of moving

fn test(x: &String) { println!("{}", x); }
test(&x);
println!("{}", x); // x never moved

Best default — the function only needs to read.

3. Clone before the call

test(x.clone());
println!("{}", x); // original untouched

Costs an allocation — use when the callee truly needs ownership.

4. Derive Copy (structs of Copy fields)

#[derive(Copy, Clone)]
struct Strct { x: u32, y: u32, z: u32 }
// now behaves like a scalar — copies on pass

Only valid if every field is itself Copy.

Summary

The rule, one more time

Everything on this deck reduces to one sentence
Reassignment is always legal. A move error only fires when you read a value after it has been moved — whether that value is a String, a plain struct, or a struct moved twice across two frames.
QuestionAnswer
Does passing x then reassigning x error?No — never, for any type
