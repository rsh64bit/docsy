Fundamentals

What is endianness?

The order CPUs store multi-byte integers in memory

Little-Endian — RISC-V, x86, ARM

LSB (least significant byte) at the lowest address.

The "little end" comes first.

uint16_t val = 0x0800;

Addr   Value
0x1000 [00] ← LSB first
0x1001 [08] ← MSB

Big-Endian — Network, PowerPC

MSB (most significant byte) at the lowest address.

The "big end" comes first. Matches how you write it.

uint16_t val = 0x0800;

Addr   Value
0x1000 [08] ← MSB first
0x1001 [00] ← LSB
Endianness only affects multi-byte integers (uint16_t, uint32_t, uint64_t). Byte arrays are identical on both architectures.

The rule

TypeEndianness matters?Why
uint8_t[], char[]NoByte-addressed, always same layout
uint16_tYes — htons()2-byte integer, order differs
uint32_tYes — htonl()4-byte integer, order differs
struct of uint8_t[]NoJust bytes in sequence
struct with mixedOnly integer fieldsByte arrays fine, integers need swap
Mental model: can you index it with [i]? → no endianness. Does the CPU load it as one value? → endianness matters.
Why?

Why does little-endian exist?

It's a hardware optimization, not a mistake

The type-casting advantage

uint8_t  val8  = 0x08;
uint16_t val16 = 0x0008;
uint32_t val32 = 0x00000008;

Little-Endian — same address works

Addr    u8      u16         u32
0x1000  [08]    [08][00]    [08][00][00][00]
         ↑       ↑           ↑
         same address, same value byte

Cast between sizes without shifting. Hardware is simpler.

Big-Endian — address shifts

Addr    u8      u16         u32
0x1000  [08]    [00][08]    [00][00][00][08]
         ↑            ↑                  ↑
         different positions each time

Widening requires address adjustment. More hardware logic.

Why the wire is big-endian

Human-readable: 0x0800 appears as [08][00] — same as you write it. Early ARPANET (1970s) chose this so the most significant bits arrive first, enabling classify-while-receiving.

Endianness = byte order. Bit order within a byte is always the same. The wire sends MSb of MSB first, LSb of LSB last.

Reading specs

How to read wire diagrams

Protocol specs use bit 0 = MSb (opposite of register convention)

Protocol diagram (RFC / IEEE)

Bit: 0  1  2  3  4  5  6  7
     ↑                    ↑
    MSb                  LSb
    (first on wire)    (last)

Bit 0 = most significant. Transmission order: left to right.

Register datasheet (HW convention)

Bit: 7  6  5  4  3  2  1  0
     ↑                    ↑
    MSb                  LSb
    (highest value)    (lowest)

Bit 0 = least significant. Value order: right to left.

Same byte, two labelings

Value: 0x08 = 0000 1000

Protocol:  bit 0  1  2  3  4  5  6  7       ← MSb is bit 0
                0  0  0  0  1  0  0  0

Register:  bit 7  6  5  4  3  2  1  0       ← LSb is bit 0
                0  0  0  0  1  0  0  0

Same data. Just numbered from opposite ends.
When reading a protocol spec, bit 0 is NOT the same bit 0 as in your PCS register datasheet. Specs count from MSb; hardware counts from LSb.
The bridge

htons() — host to network

The bridge between CPU byte order and wire byte order
uint16_t type = 0x0800;   // in CPU register

// Without htons — WRONG on little-endian
Memory: [00] [08]   ← wire sees 0x0008 → frame dropped!

// With htons — CORRECT
type = htons(0x0800);    // swaps to 0x0008 in register
Memory: [08] [00]   ← wire sees 0x0800 → IPv4 recognized

The full family

FunctionDirectionSize
htons()Host → Networkuint16_t
ntohs()Network → Hostuint16_t
htonl()Host → Networkuint32_t
ntohl()Network → Hostuint32_t
On a big-endian CPU these are all no-ops — the byte order already matches. On little-endian they swap. Your code calls them regardless; the compiler optimizes away the no-op case.

Fix

The fix: shifts & masks

You control exactly where each field lands — portable, no surprises
// pt=0xA, C=1, ind=0x5

buf[0] = (pt << 4) | (C << 3) | ind;

pt  << 4:   [1  0  1  0  0  0  0  0]
C   << 3:   [0  0  0  0  1  0  0  0]
ind     :   [0  0  0  0  0  1  0  1]
            ─────────────────────────────
OR result:  [1  0  1  0  1  1  0  1] = 0xAD

Bit:         7  6  5  4  3  2  1  0
            [pt       ][C][ ind    ]  ← matches spec exactly

Accessor macros (Zephyr style)

/* Getters */
#define GET_PT(b)    ((b) >> 4)
#define GET_C(b)     (((b) >> 3) & 0x1)
#define GET_IND(b)   ((b) & 0x7)

/* Setter */
#define SET_BYTE0(pt, c, ind)  (((pt) << 4) | ((c) << 3) | (ind))
This is exactly what your adi_hal_ethernet_regmap_regmap.h does — BM_ (bitmask) and BP_ (bit position) macros with shifts. Same principle for registers and wire protocols.
